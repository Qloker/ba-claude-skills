# Skill: Вариант использования (Use Case)

Скилл генерирует **один сводный .docx документ** на модуль системы. Документ содержит:

1. Заголовок и краткое описание модуля
2. Все варианты использования модуля (каждый — со своими 13 полями Коберна)
3. Справочные таблицы данных (если в UC фигурируют сущности с формами или экраны со списками)
4. Сводную таблицу функциональных требований (FR), сгруппированную по UC
5. Раздел перекрёстных ссылок между FR
6. Таблицу нефункциональных требований (NFR) — **только если пользователь явно попросил**

Полный эталонный пример структуры — в `references/example_summary_document.md` (на основе реального документа «Панель администратора SCADA»). Сверяйся с ним перед генерацией.

## Принцип «Данные отдельно — требования ссылаются»

> **Ключевое правило.** Если в требованиях фигурируют конкретные поля сущности (карточка пользователя, форма роли, столбцы журнала, поля фильтра) — они выносятся в **справочную таблицу данных**. В тексте UC и в FR вместо перечисления полей ставится **ссылка на справочную таблицу**.

### Зачем

- **Единый источник истины.** Поле добавляется/удаляется — обновляется одна таблица, а не десятки строк FR.
- **Поддержка.** Разработчик всегда знает, где смотреть актуальный состав полей.
- **Читаемость FR.** Критерии становятся компактнее.

### Когда нужна справочная таблица

- **Сущность с формой** (карточка пользователя, форма роли) → таблица «Данные [сущности]» с колонками: №, Поле, Тип данных, Обязательное, Уникальное, Правила/Примечание.
- **Экран со списком** (список пользователей, журнал) → таблица «Данные таблицы [экрана]» с колонками: №, Столбец, Источник данных, Формат отображения, Сортировка, Примечание.

### Что согласовать с пользователем перед заполнением

Не додумывай — спрашивай (через AskUserQuestion при 2+ вопросах):

- Какие поля обязательны?
- Какие уникальны?
- Доступен ли поиск/сортировка по полю?
- Есть ли фильтры, зависимости между полями?
- Формат отображения (моноширинный шрифт, badge, дата)?

### Как ссылаться из FR

**Не пиши:** «Описание: Система открывает форму с полями: Фамилия, Имя, Email, Роль…»

**Пиши:** «Описание: Система открывает форму регистрации. Состав полей — согласно таблице "Данные пользователя".»

Шаблоны ссылок:
- «Состав полей формы — согласно таблице "Данные [сущности]".»
- «Столбцы — согласно таблице "Данные таблицы [экрана]".»
- «Правила валидации — согласно таблице "Данные [сущности]".»
- «Система сохраняет данные согласно таблице "Данные [сущности]".»

## Часть 1. Структура каждого UC — 13 полей Коберна

Заполни все 13 полей в указанном порядке. Если данных нет, ставь «Требует уточнения».

| № | Поле | Назначение |
|---|------|-----------|
| 1 | **Название (Title)** | В заголовке UC. Краткая фраза в активном залоге: глагол + объект. Пример: «Зарегистрировать пользователя», «Снять наличные». |
| 2 | **Основное действующее лицо (Primary Actor)** | Кто инициирует. Пример: «Администратор системы», «Внешний платёжный сервис». |
| 3 | **Область действия (Scope)** | Граница системы. Пример: «Панель администратора SCADA-системы (модуль IAM)». |
| 4 | **Уровень (Level)** | Суммарный / **Цель пользователя** (предпочтительно) / Подфункция. |
| 5 | **Участники и интересы** | Список «[Участник] — [его интерес]». Включай всех стейкхолдеров, даже если они не действуют напрямую. |
| 6 | **Предусловия** | Что гарантированно истинно до запуска UC. Внутри сценария не проверяется повторно. Если условий ≥2 — оформляются как **отдельные Normal-параграфы с ручной нумерацией в тексте** («1. …», «2. …»); если одно — обычный параграф `<bold>Предусловия:</bold> <текст>`. **Не используй стиль `List Number`** — у него общий счётчик через весь документ, и нумерация в следующем UC продолжится с предыдущего вместо «1». Ручная нумерация в Normal гарантирует, что каждый UC стартует с «1.». |
| 7 | **Минимальные гарантии** | Что система обещает всем участникам независимо от исхода. Пример: «Попытка записана в лог». |
| 8 | **Гарантия успеха (Postconditions)** | Состояние после успешного завершения. |
| 9 | **Триггер** | Конкретное внешнее событие, запускающее UC. |
| 10 | **Основной сценарий успеха** | Идеальный путь без ветвлений. Шаги 1, 2, 3… См. правила ниже. |
| 11 | **Расширения** | Все отклонения. См. отдельный раздел. |
| 12 | **Вариации технологий и данных** | Различные способы реализации шагов без изменения логики. Пример: «1а. Идентификация по карте или отпечатку». |
| 13 | **Открытые вопросы** | Нерешённые вопросы для бизнеса/архитекторов. |

### Жирный шрифт для названий полей (важно)

В docx названия 8 полей шапки UC (поля 2–9 из таблицы выше) оформляются **жирным шрифтом** в начале строки, дальше идёт значение обычным шрифтом. Это даёт быстрое визуальное сканирование UC и совпадает с реальным эталоном заказчика.

Жирные ярлыки:
- **Основное действующее лицо:**
- **Область действия:**
- **Уровень:**
- **Участники и интересы** (только сам заголовок над списком — bullet'ы под ним обычные)
- **Предусловия:** (если ≥2 пунктов — ярлык на отдельном параграфе, под ним Normal-параграфы с ручной нумерацией «1. …», «2. …»; если одно условие — `<bold>Предусловия:</bold> <текст>` в одном параграфе)
- **Минимальные гарантии:**
- **Гарантия успеха:**
- **Триггер:**

Реализация в python-docx — bold run внутри одного параграфа:

```python
p = doc.add_paragraph()
p.add_run("Основное действующее лицо: ").bold = True
p.add_run("Диспетчер SCADA")
```

Не используй маркдаун-звёздочки `**текст**` в docx — это будет напечатано как литералы. Только bold run через `run.bold = True`.

### Правила основного сценария

- **Никаких «если»** в основном сценарии — все ветвления уходят в расширения.
- Каждый шаг показывает заметный прогресс к цели.
- Формат шага: «[Субъект] [действие]». Чередуй актора и систему.
- **3–9 шагов оптимально.** 10–11 — допустимо для сложных взаимодействий. 12+ — недопустимо: объединяй шаги или выноси часть в подфункцию.

### Расширения — правила нумерации

Каждое расширение состоит из:
1. **Условие:** `[номер шага][буква]. [событие]:` — например, `3а. Недостаточно средств на счёте:`. **Эта строка целиком оформляется жирным шрифтом** (bold run) — она работает визуальным заголовком ветки. Подшаги под ней — обычные.
2. **Реакция:** подшаги `3а1.`, `3а2.`… (обычный шрифт)
3. **Исход:** отдельный нумерованный подшаг — «Возврат к шагу X.», «Вариант использования завершается успешно/неудачей.», «Переход к [другой UC].» (обычный шрифт)

Реализация в python-docx:

```python
# Условие расширения — жирный
p = doc.add_paragraph()
p.add_run("2а. У диспетчера уже есть активная (незакрытая) смена в системе:").bold = True

# Подшаги — обычные параграфы
doc.add_paragraph("2а1. Система отображает сообщение: «У вас уже есть открытая смена…»")
doc.add_paragraph("2а2. Система предлагает перейти к карточке активной смены.")
doc.add_paragraph("2а3. Вариант использования завершается неудачей.")
```

**КРИТИЧЕСКИ ВАЖНО: исход — отдельный нумерованный подшаг, а не продолжение предыдущего.**

❌ Неправильно (склейка через `→`, `—`, «и»):
```
2а3. Клиент вводит новую сумму → Возврат к шагу 2.
3а2. Система отменяет транзакцию — Вариант использования завершается неудачей.
```

✅ Правильно (исход — отдельная строка с собственным номером):
```
2а3. Клиент вводит новую сумму.
2а4. Возврат к шагу 2.

3а2. Система отменяет транзакцию.
3а3. Вариант использования завершается неудачей.
```

Это правило применяется ко всем исходам: «Возврат к шагу X.», «Вариант использования завершается успешно/неудачей.», «Переход к [другой UC].»

Никаких стрелок `→`, тире `—` или союза «и» для склейки действия с исходом. **В docx каждый подшаг — отдельный параграф,** без символов-разделителей внутри строки.

Если внутри расширения возникает своё ветвление, используй вложенную нумерацию: `2а3а.`, `2а3б.`

Типы расширений:
- **Альтернативный путь успеха** — иной способ достичь цели (не ошибка). Заканчивается успехом.
- **Условие ошибки / Исключение** — препятствие. Система либо помогает исправить (Repair → возврат), либо фиксирует минимальные гарантии и завершает работу (Failure).

## Часть 3. Сводная таблица функциональных требований (FR)

В сводном документе **FR группируются по UC**: один раздел H2 на UC, внутри — таблица.

```
H1: Сводная таблица функциональных требований (FR)
  Параграф-вступление: «Требования сгруппированы по вариантам использования.
                      Дублирующие требования объединены и имеют перекрёстные ссылки.»
  H2: UC-XXX-01: [Название]
    Таблица: Код | Название | Описание | Критерии приёмки
  H2: UC-XXX-02: [Название]
    Таблица: ...
  ...
```

Коды FR — `FR-UC[N]-NN`, где N — номер UC, NN — порядковый. Пример: `FR-UC1-01`, `FR-UC1-02`, `FR-UC3-04`.

### Правила написания критериев приёмки

**Принцип.** Критерий — проверяемое утверждение на языке бизнес-логики. Два независимых наблюдателя должны прийти к одному выводу.

**Уровень абстракции — бизнес-логика, без деталей реализации:**
- Пиши «Система изменяет статус пользователя на "Удалён"», а НЕ «В БД поле status = deleted».
- Пиши «Активные сессии завершены», а НЕ «API вызывает endpoint /logout».
- Пиши «Удалённые визуально отличаются от активных», а НЕ «Badge красного цвета, opacity 0.45».

**Не упоминай:** БД, поля таблиц, SQL, API, HTTP-коды, транзакции, timestamps.

**Не диктуй визуальный дизайн:** цвета кнопок, стили badge, непрозрачность, шрифты. Это зона дизайнера.

**Антипаттерны:**

| Плохо | Почему | Хорошо |
|-------|--------|--------|
| «ФИО отображается корректно» | Непроверяемо | «ФИО в формате: Фамилия (жирный) Имя Отчество» |
| «Данные сохранены» | Расплывчато | «Система сохраняет данные согласно таблице "Данные пользователя"» |
| «Кнопки отображаются» | Какие? Где? | «Модальное окно содержит кнопки "Подтвердить" и "Отмена". Фокус по умолчанию на "Отмена"» |
| «Ошибка показывается» | Какая? Когда? | «Сообщение под полем Email: "Пользователь с таким email уже существует". Видно до исправления» |
| «В БД поле status = deleted» | Реализация | «Система изменяет статус на "Удалён"» |

**Правила хороших критериев:**

1. **Бизнес-язык** — что система делает для пользователя, не как реализовано.
2. **Не диктуй дизайн** — описывай поведение, а не цвета/стили.
3. **Что ИМЕННО** — конкретное поведение и состояние.
4. **Когда** — момент проверки: при открытии, blur, после сохранения.
5. **Дефолтное состояние** — если есть: пустые поля, фокус на кнопке, начальный фильтр.
6. **Ссылка на справочник** заменяет перечисление полей.
7. **3–5 критериев на FR** — оптимально. 1–2 мало. 6+ — разбей FR.

### Пример хорошего FR

| FR-UC1-01 | Отобразить форму регистрации | Система открывает форму регистрации. Состав полей — согласно таблице «Данные пользователя». | 1. При открытии все поля пустые, курсор в первом поле (Фамилия). 2. Обязательные поля отмечены (*) согласно таблице «Данные пользователя». 3. Поле «Роль» — выпадающий список из справочника ролей; первое значение — placeholder «Выберите роль». 4. Область доступа — дерево с чекбоксами, свёрнуто по умолчанию. |

Больше примеров — в `references/example_summary_document.md`.

## Часть 4. Перекрёстные ссылки между FR

В конце сводной FR-таблицы добавь раздел **«Перекрёстные ссылки и пересечения FR»** (стиль Heading 2). Это bullet-список, показывающий какие FR переиспользуются между UC. Формат каждого пункта:

> `FR-UC[N]-NN (краткое название)` → применима в `UC-XXX-XX` и `UC-XXX-YY`. Единая логика: [короткое описание общей логики].

Реальные примеры из SCADA IAM:

- FR-UC1-02 (Валидация email при blur) → применима в UC-ADM-01 и UC-ADM-02. Единая логика: формат RFC 5322 + уникальность.
- FR-UC1-06 (Отправка ссылки для входа) → используется в UC-ADM-01 (регистрация) и UC-ADM-04 (восстановление).
- FR-UC3-03 (Деактивация в сервисе аутентификации) ↔ FR-UC4-03 (Активация в сервисе аутентификации) — обратные операции.

**Когда добавлять.** Если в модуле ≥2 UC и есть хотя бы одно повторение требований между ними. Если повторений нет — раздел можно опустить.

## Часть 5. Нефункциональные требования (NFR) — опциональный блок

**Добавляй ТОЛЬКО если пользователь явно попросил** или указал нефункциональные характеристики (производительность, безопасность, нагрузку, доступность). По умолчанию NFR не генерируется — это решение пользователя для сохранения фокуса на сценариях.

Шаблон таблицы NFR (одна общая таблица в конце документа):

| ID | Категория | Описание | Метрика / Критерий |
|----|-----------|----------|-------------------|
| NFR-01 | Производительность | Время отклика формы при сохранении | Не более 3 секунд для 95% запросов при стандартной нагрузке |
| NFR-02 | Безопасность | Передача данных в сервис аутентификации | Взаимодействие по HTTPS (TLS 1.2+). Пароль не передаётся. |
| NFR-03 | Безопасность | Доступ к функции | Только пользователи с соответствующим атрибутом. HTTP 403 при попытке доступа без атрибута. |
| NFR-04 | Удобство | Форма доступна оператору с базовыми навыками | Обязательные поля имеют визуальную маркировку. Ошибки рядом с полями. |

Категории: Производительность, Безопасность, Удобство использования, Надёжность, Совместимость, Масштабируемость.

## Структура итогового .docx — иерархия стилей

Используй именно эти стили python-docx (важно для навигации в Word и согласованности с реальными документами заказчика):

```
Heading 1: Варианты использования: [Название модуля]
Normal:    [Описание модуля — 1-3 предложения]

Heading 1: UC-XXX-01: [Название первого UC]
Normal:    <bold>Основное действующее лицо:</bold> ...
Normal:    <bold>Область действия:</bold> ...
Normal:    <bold>Уровень:</bold> ...
Normal:    <bold>Участники и интересы</bold>
List Bullet:  Администратор — хочет ...
```

### Технические правила docx

- Используй **python-docx** (`pip install python-docx`). Для Windows: `$env:PYTHONUTF8=1`.
- Применяй стили через `doc.add_paragraph(text, style='Heading 1' | 'Heading 2' | 'Normal' | 'List Bullet')`.
- Таблица: `doc.add_table(rows=N, cols=M)` + установка ширины колонок через OxmlElement.
- Используй `ShadingType.CLEAR` для заливки, никогда `SOLID`.
- Никогда не используй `\n` внутри ячейки — только отдельные параграфы внутри ячейки (`cell.add_paragraph()`).
- Каждый подшаг расширения — **отдельный параграф**, без символов-разделителей. Без `→`, `—`, «и».
- Сохраняй файл в директорию проекта пользователя, имя в формате `UC_[Модуль]_[Описание].docx` (например, `UC_ADM_Panel_Administratora.docx`).

## Рабочий процесс

1. **Сбор информации.** Если пользователь описал задачу кратко — задай уточняющие вопросы: какие UC входят в модуль, кто актор, что является системой, есть ли особые бизнес-правила. При 2+ вопросах используй AskUserQuestion.

2. **Заполнение UC.** Заполни все 13 полей для каждого UC. Не пропускай поля — если нет данных, ставь «Требует уточнения».

3. **Проверка основного сценария.** Никаких «если» — всё в расширения. Проверь количество шагов (3–9, до 11 в крайнем случае).

4. **Расширения.** Минимум 2–3 расширения на UC: типичные ошибки ввода, отказ внешних систем, альтернативные пути. Каждый исход — отдельный нумерованный подшаг.

5. **Справочные таблицы.** Выдели сущности и экраны, создай таблицы. **Согласуй с пользователем** обязательность, уникальность, фильтры — не додумывай.

6. **FR.** Из сценария выдели технически сложные шаги → оформи FR. В описаниях и критериях **ссылайся на справочники**, не перечисляй поля.

7. **Перекрёстные ссылки.** Если есть переиспользуемые FR — добавь раздел.

8. **NFR.** Только если пользователь явно попросил.

9. **Генерация .docx.** Используй python-docx, иерархию стилей выше. Сохрани файл в директорию пользователя.

10. **Вывод.** Дай ссылку на файл. В чат — только краткое резюме (что сделано, сколько UC, сколько FR, где файл).
