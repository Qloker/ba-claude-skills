# Skill: Вариант использования (Use Case)

Этот Skill учит создавать требования в формате «Вариант использования» строго по шаблону пользователя.
Каждый документ состоит из двух частей: **описания ВИ** (13 полей) и **таблиц требований** (FR + NFR).

---

## Структура документа

### Часть 1. Описание варианта использования

Заполни все 13 полей строго в указанном порядке.

**1. Название (Title)**
Краткая фраза в активном залоге: глагол + объект. Отражает результат, а не процесс.
*Пример:* «Снять наличные», «Оформить заказ», «Авторизоваться в системе».

**2. Основное действующее лицо (Primary Actor)**
Участник (человек или внешняя система), который инициирует взаимодействие.
*Пример:* «Клиент банка», «Менеджер по продажам», «Внешний платёжный сервис».

**3. Область действия (Scope)**
Граница проектируемой системы — что является «чёрным ящиком».
*Пример:* «Банкомат», «Веб-приложение интернет-магазина».

**4. Уровень (Level)**
Место цели в иерархии. Допустимые значения:
- **Суммарный** — охватывает несколько целей пользователя
- **Цель пользователя** (sea level) — достигается за один присест ✓ (предпочтительный уровень)
- **Подфункция** — часть цели пользователя

**5. Участники и интересы (Stakeholders and Interests)**
Список лиц/организаций, чьи интересы защищает система, даже если они не участвуют напрямую.
Формат: «[Участник] — [его интерес]».
*Пример:* «Налоговое управление — хочет гарантировать регистрацию транзакции».

**6. Предусловие (Precondition)**
Состояние системы, гарантированное истинным до запуска ВИ. Внутри сценария эти условия не проверяются повторно.
*Пример:* «Пользователь авторизован в системе», «Корзина содержит хотя бы один товар».

**7. Минимальные гарантии (Minimal Guarantees)**
Наименьшее обещание системы всем участникам — выполняется независимо от успеха или провала сценария.
*Пример:* «Попытка транзакции записана в лог».

**8. Гарантия успеха (Success Guarantees / Postconditions)**
Состояние системы после успешного завершения — все интересы стейкхолдеров удовлетворены.
*Пример:* «Средства списаны со счёта, наличные выданы, квитанция напечатана».

**9. Триггер (Trigger)**
Конкретное внешнее событие, запускающее ВИ.
*Пример:* «Клиент вставляет карту в картридер», «Пользователь нажимает кнопку "Оформить заказ"».

**10. Основной сценарий успеха (Main Success Scenario)**
Идеальное развитие событий без ошибок и ветвлений.

Правила написания:
- **Никаких "если" внутри основного сценария** — все ветвления выносятся в расширения.
- Каждый шаг показывает заметный прогресс к цели.
- Шаги нумеруются: 1, 2, 3...
- Формат шага: «[Субъект] [действие]». Чередуй актора и систему.

**Правило количества шагов:**
- **3–9 шагов** — оптимально: хорошо читается, легко воспринимается.
- **10–11 шагов** — допустимо только для объективно сложных взаимодействий.
- **12+ шагов** — недопустимо. Необходимо оптимизировать: объединяй логически связанные действия в один шаг. Например, вместо «Система открывает модальное окно» + «Система загружает данные пользователя» — один шаг: «Система открывает модальное окно и загружает данные пользователя». Если объединение невозможно — пересмотри границы ВИ и вынеси часть шагов в отдельный вариант использования уровня «Подфункция».

*Пример:*
1. Клиент вводит сумму снятия.
2. Система проверяет остаток на счёте.
3. Система резервирует сумму и открывает лоток.
4. Клиент забирает наличные.
5. Система фиксирует транзакцию и печатает квитанцию.

**11. Расширения (Extensions)**
Все отклонения от основного сценария — как альтернативные успешные пути, так и ошибки.

Правила написания расширений:
- Привязка к номеру шага: `3а`, `3б`, `4а`...
- Структура записи каждого расширения:
  1. **Условие:** `[номер шага][буква]. [краткое описание события]:` — например, `3а. Недостаточно средств на счёте:`
  2. **Реакция:** список подшагов `3а1.`, `3а2.`... описывающих действия системы
  3. **Выход:** отдельный нумерованный подшаг — «Возврат к шагу X.», «Вариант использования завершается успешно.», «Вариант использования завершается неудачей.» или «Переход к [другой ВИ].»
- **Продолжай нумерацию после точки развилки.** Не ставь только точку разветвления — после `3а.` всегда идут `3а1.`, `3а2.` и т.д.
- Если внутри расширения возникает своё ветвление, используй: `3а2а.`, `3а2б.`

**КРИТИЧЕСКИ ВАЖНО: Исход расширения — отдельный подшаг, а не продолжение предыдущего.**

❌ **Неправильно** (исход склеен с действием через стрелку `→` или тире):
```
2а3. Клиент вводит новую сумму → Возврат к шагу 2.
3а2. Система отменяет транзакцию — Вариант использования завершается неудачей.
```

✅ **Правильно** (исход — отдельный нумерованный подшаг на новой строке):
```
2а3. Клиент вводит новую сумму.
2а4. Возврат к шагу 2.

3а2. Система отменяет транзакцию.
3а3. Вариант использования завершается неудачей.
```

Это правило применяется ко всем типам исходов расширения:
- «Возврат к шагу X.»
- «Вариант использования завершается успешно.»
- «Вариант использования завершается неудачей.»
- «Переход к [другой ВИ].»

Никогда не используй стрелки `→`, тире `—` или союз «и» для склейки действия с исходом в одном шаге. Исход всегда на отдельной строке с собственным номером подшага. Это же правило распространяется и на генерацию документов (`.docx`, `.md`, `.html`): каждый подшаг — отдельный абзац / отдельный `Paragraph`, без символов-разделителей внутри строки.

Типы расширений:
- **Альтернативный путь успеха** — иной способ достичь цели (не ошибка). Завершается Гарантией успеха.
- **Условие ошибки / Исключение** — препятствие. Система либо помогает исправить (Repair → возврат в сценарий), либо фиксирует минимальные гарантии и завершает работу (Failure).

*Пример расширения:*
```
2а. Недостаточно средств на счёте:
  2а1. Система уведомляет клиента о недостатке средств.
  2а2. Система предлагает ввести меньшую сумму.
  2а3. Клиент вводит новую сумму.
  2а4. Возврат к шагу 2.
  — или —
  2а3а. Клиент отказывается.
  2а3б. Вариант использования завершается неудачей.
```

**12. Вариации технологий и данных (Technology & Data Variations List)**
Список различных способов реализации шагов, не меняющих логику намерений актора.
*Пример:* «1а. Идентификация по карте или по отпечатку пальца».

**13. Открытые вопросы (Open Issues)**
Нерешённые проблемы, требующие уточнения у бизнеса или архитекторов.
*Пример:* «Каков период хранения невостребованных логов?»

## Часть 2. Таблицы требований

### Таблица FR — Функциональные требования

Для каждого сложного шага основного сценария или расширения, требующего технической детализации, создай запись.

| Код | Название | Описание | Критерии приёмки |
|:----|:---------|:---------|:-----------------|
| FR-UC[N]-01 | Глагол + Объект | Что делает система | Список проверяемых условий по правилу SMART |

**Правило SMART для критериев приёмки:**
Критерии должны быть конкретными, измеримыми, достижимыми, актуальными и ограниченными.
Разные независимые наблюдатели должны прийти к одному выводу — выполнен критерий или нет.

*Пример:*
| FR-UC1-01 | Проверить баланс | Система запрашивает текущий баланс счёта в процессинговом центре | 1. Ответ получен за ≤2 сек в 95% случаев. 2. При балансе < запрошенной суммы — отказ с кодом ERR-101. |

### Таблица NFR — Нефункциональные требования

Источник — раздел «Особые требования» ВИ. Каждое требование должно быть измеримым.

| ID | Категория | Описание (сценарий качества) | Метрика / Критерий оценки |
|:---|:----------|:-----------------------------|:--------------------------|
| NFR-01 | Производительность | Время реакции системы при [Триггер] в условиях [Окружение] | Не более X секунд для 95% запросов |
| NFR-02 | Безопасность | Ограничение доступа или правила шифрования | Соответствие стандарту (например, TLS 1.2+) |
| NFR-03 | Надёжность | Время восстановления после сбоя или доступность | MTTR < 5 минут или 99.9% uptime |

## Рабочий процесс

1. **Сбор информации.** Если пользователь описал задачу кратко — задай уточняющие вопросы: кто актор, что является системой, какова цель, есть ли особые бизнес-правила.

2. **Заполнение ВИ.** Заполни все 13 полей. Не пропускай поля — если данных нет, укажи «Требует уточнения».

3. **Проверка основного сценария.** Убедись, что в нём нет «если» — все ветвления вынесены в расширения.

4. **Расширения.** Предусмотри как минимум 2–3 расширения: типичные ошибки ввода, отказ внешних систем, альтернативные пути.

5. **Таблицы FR/NFR.** Выдели из сценария технически сложные шаги → оформи FR. Добавь NFR по нефункциональным аспектам (скорость, безопасность, надёжность).

6. **Вывод.** Сохрани готовый документ как `.docx` файл в папку `/sessions/kind-awesome-lamport/mnt/Docs CC/`. Имя файла — транслитерация названия ВИ, например `zakazat-tovar.docx`.

   Для создания .docx используй npm-пакет `docx` (установка: `npm install -g docx`). Создай JavaScript-скрипт и запусти его через Node.js.

   Структура документа:
   - Заголовок H1: название ВИ
   - Разделы 1–9: Heading2 + обычный текст (Paragraph)
   - Раздел 10 (Основной сценарий): нумерованный список через `LevelFormat.DECIMAL`
   - Раздел 11 (Расширения): форматированный текст с подпунктами
   - Разделы 12–13: обычный текст / список
   - Таблица FR: полноширинная таблица (ширина 9026 DXA для A4) с заголовочной строкой (серая заливка `D5E8F0`, жирный шрифт) и 4 столбцами: Код (1200), Название (2000), Описание (3000), Критерии приёмки (2826)
   - Таблица NFR: аналогичная таблица с 4 столбцами: ID (700), Категория (1400), Описание (4000), Метрика (2926)

   Критические правила docx:
   - Всегда задавай `width` И `columnWidths` у таблицы, а также `width` у каждой ячейки (WidthType.DXA)
   - Используй `ShadingType.CLEAR` для заливки, никогда SOLID
   - Добавляй `margins: { top: 80, bottom: 80, left: 120, right: 120 }` ко всем ячейкам
   - Никогда не используй `\n` — только отдельные Paragraph-элементы
   - Никогда не вставляй символы буллетов вручную — только через `LevelFormat.BULLET`

   После создания проверь файл: `python /sessions/kind-awesome-lamport/mnt/.claude/skills/docx/scripts/office/validate.py <путь к файлу>`

   Предоставь ссылку на файл через `computer://` путь. В чат выводи только краткое резюме (название, актор, количество шагов и расширений) и ссылку.

## Пример готового документа (краткий)

```
## Вариант использования: Авторизоваться в системе

**Основное действующее лицо:** Зарегистрированный пользователь
**Область действия:** Веб-приложение
**Уровень:** Цель пользователя
**Предусловие:** Пользователь открыл страницу входа
**Минимальные гарантии:** Попытка входа записана в журнал безопасности
**Гарантия успеха:** Пользователь получил доступ к личному кабинету
**Триггер:** Пользователь нажимает кнопку «Войти»

### Основной сценарий успеха
1. Пользователь вводит логин и пароль.
2. Система проверяет учётные данные.
3. Система создаёт сессию и перенаправляет в личный кабинет.

### Расширения
2а. Неверный пароль:
  2а1. Система уведомляет об ошибке и предлагает повторить попытку.
  2а2. Пользователь повторяет ввод → Возврат к шагу 1.
  — или —
  2а2а. После 3 неудачных попыток система блокирует аккаунт на 15 минут → Вариант использования завершается неудачей.
```
